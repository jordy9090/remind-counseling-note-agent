# Individual beta enrollment and erasure

The Re:mind operator maintains the enrollment register. The participating counselor verifies the client and their choices, keeps the signed form at the institution, and communicates with the client. Do not put client names, contact information, clinical text, or signed forms in the register, SQL history, email, or technical logs.

## Start a case

1. Obtain the individual consent for the applicable deployed data path and the processing choices that will be used. Record the actual signature time (Korea time). A voluntary withdrawal takes effect regardless of how many sessions were completed.
2. Allocate a random receipt UUID, record it on the institution's copy, and verify the counselor's Supabase Auth UUID. Using the administrator SQL connection, call `select beta_retention.enroll(:receipt, :owner, :signed_at)` with bound values. On retry use the same three values. This creates a fresh, alias-only case. The counselor selects that case in the authenticated workspace before entering material. Do not import historical cases or attach an unrelated client's case.
3. For beta material, work inside that case. Unassigned quick summaries, guest-to-login drafts and downloads have no case-bound server erasure guarantee. Use the case workflow for beta material. If a counselor makes an authorized institutional export, record its custody separately. The service cannot erase an institution's own records or a download from its device.
4. When consent choices exclude a provider or recording, omit that operation. If a required operation is declined, continue counseling through the institution's usual process.

## End or withdraw

- The database scheduler runs every minute. It removes registered service material at 168 hours after signature. It never enrolls existing cases by date or account. Check the named job in `cron.job` and its latest run status in `cron.job_run_details` each working day and following an outage or restore. Re-run `select beta_retention.erase_due()` after recovery, before making a restored database available. Reconcile any restores with the institution's withdrawal receipts to prevent resurrection.
- On receipt of a request, the counselor records its date, verifies the client, stops new processing, closes any open case tabs, and gives the operator only the receipt and the counselor account identifier. The operator runs `select beta_retention.withdraw(:receipt, :owner)`. For an already expired case, verify the existing receipt. Retry the same identifiers if interrupted. Both operations cover active cases, sessions, turns/windows, memory vectors, notes and evidence, drafts, export history, vouchers and their application recovery copies.
- Check `select receipt, ends_at, withdrawn_at, erased_at, notified_at from beta_retention.enrollments where receipt=:receipt and owner_id=:owner`. If erasure failed, keep the request open, investigate the job status without viewing clinical content, retry, and record the actual outcome. A missing receipt alone proves nothing. The counselor checks local tabs, downloads, printed copies and institution-held originals separately. Close out any permitted provider assistance, outstanding transfers or temporary files, and follow up on residual provider copies under applicable terms.
- The counselor communicates the outcome within ten days of **receiving** a deletion request, including any outstanding copies or applicable restrictions. The operator records the actual notification time only after the counselor confirms it, using `update beta_retention.enrollments set notified_at=coalesce(notified_at, now()) where receipt=:receipt and owner_id=:owner and erased_at is not null`. Keep the original request date and pending notifications in the institution's separate, access-controlled duty register until closed. A database completion timestamp is not a notification.
- The database discards content-free enrollment and deletion metadata one calendar year after the end or earlier withdrawal. The institution applies the same policy to its beta consent and request evidence under its control. Any official institution records subject to separate duties have their own retention basis. No administrator credentials, service role, client account, or project deletion are required in the counseling application.

## Release and verification

Apply the versioned migration before enrollment. Enable the iwinv unit's no-disk recomposition and disabled embedding-cache settings before receiving beta data. Use a protected operator account and keep the private schema outside PostgREST. Test the SQL fixture only in a transaction with an empty enrollment registry. It rolls back synthetic Auth users and rows. This procedure verifies logical removal of service-controlled records; it does not certify physical media or provider-managed backup expiry.
